# CLAUDE.md — Working rules for this repo

Read this before making changes. It captures decisions already made so they don't get re-litigated or accidentally reversed.

## Code style

- Beginner-friendly, readable code over clever code. No unnecessary abstractions.
- No comments explaining *what* code does — only *why*, when it's non-obvious (a security reason, a workaround, a subtle invariant).
- Don't add validation, error handling, or config for scenarios that can't happen yet. Don't build for hypothetical future requirements.
- Don't hardcode domain values we've explicitly deferred (e.g. staff role names like "Doctor"/"Nurse" — those come from the future dynamic AccessRole system, not an enum).

## Backend structure (layer-based, not feature-nested)

```
backend/
  app.ts          Express app: middleware, routes, central error handler
  server.ts       Startup only: dotenv.config() → connectToDatabase() → app.listen()
  config/         env.ts (all env var reads), db.ts, cors.ts, permissions.ts (the permission catalogue),
                  dataCategories.ts (consent catalogue), vitals.ts (the sepsis model's seven vitals + ranges)
  models/         Mongoose schemas
  controllers/    HTTP req/res only — thin, no business logic
  domain/         Business logic (the "service" layer). Controllers call this.
  routes/         Route wiring: validator → middleware → controller
  middleware/     requireAuth, requirePortal, requirePermission
  validators/     Request-shape checks only (presence/type/size, via field.validator.ts's shared
                  requireString/requirePassword/requireStringArray/optionalNumberInRange/
                  requireIsoDate). Business rules live in domain/.
  utils/          hash, jwt, otp, email, refreshToken, password, httpError, mongoError
  scripts/        One-off scripts (seedOwner.ts, replayVitals.ts), not part of the running app
  tests/          vitest + supertest
```

`ml-service/` (top level, beside `backend/`, outside the npm workspace) is the sepsis model's own FastAPI service — a separate Python process the backend calls over HTTP. See "Vitals, sepsis scoring & alerts" below.

Do not reintroduce a `src/` wrapper or a feature-nested `modules/` structure unless there's a strong technical reason — this was deliberately flattened.

- **A field can be required for one creation path without being required on the `User` schema itself.** `User.phone` is a real example: required for self-registration (enforced in `validators/auth.validator.ts::validateRegister`, passed through `registerUser`), but optional at the schema level (`models/user.model.ts`) because other ways a `User` gets created — an Owner-provisioned hospital administrator, most obviously — never collect one. Making it schema-`required: true` would break those paths. When a new field is only meaningful for *some* creation flows, enforce it in that flow's validator, not in the shared schema.

## The dotenv-ordering trap (has bitten us twice — don't reintroduce it)

`dotenv.config()` must run before any other local import that reads `process.env` at module load time. Under CommonJS (`server.ts`, `scripts/*.ts`), imports execute in file order, so `dotenv.config()` must be the literal first lines. Under Vitest's real ESM (`tests/*.test.ts`), a test file's own imports are *fully evaluated* before any of that file's own statements run, so putting `dotenv.config()` first in a test file does **not** work — it must live in `tests/setup.ts` (a Vitest `setupFiles` entry), which runs as a separate step before the test module graph loads.

## Error handling

Every error a controller sees should end up as `next(err)`, flowing to the single central handler in `app.ts`. Three error shapes are recognized there and turned into clean JSON responses:
- `HttpError` (`utils/httpError.ts`) — thrown deliberately by validators/domain code, carries its own status code.
- `mongoose.Error.CastError` — thrown automatically by Mongoose whenever a client-supplied id isn't a valid ObjectId (e.g. `findById("not-an-id")`). Caught centrally and turned into a clean `400 "Invalid ID format."` — **don't** add per-route `mongoose.Types.ObjectId.isValid(...)` checks in validators for this; the one central handler already covers every route, present and future.
- **MongoDB duplicate-key errors (`code: 11000`, `utils/mongoError.ts::isDuplicateKeyError`)** — turned into a generic `409`. Every unique index in this app guards a real rule, and each has an application-level pre-check that produces a friendlier message, but a pre-check is read-then-write so a genuine race still reaches here; without this branch the indexes the model comments call "the backstop" surfaced as an unexplained `500`. The response is deliberately generic — `err.keyValue` holds the conflicting values (emails included), so it is never echoed to the client or logged. Add a pre-check for a *better message* (as `createAccessRole` does for a duplicate role name), never to replace this net.

Anything else falls through to a generic `500` with the real error only logged server-side, never sent to the client.

## Security boundaries — non-negotiable

- **The backend is the authorization source of truth.** Never trust a frontend-supplied ID (e.g. `hospitalId`) without re-verifying it server-side against the database on every request that matters.
- The access JWT carries only `{ id, portal, hospitalId? }`. `portal`/`hospitalId` are *context*, not permissions — never put roles or permissions in the token. Every permission-sensitive read goes back to the database.
- `JWT_SECRET` (`config/env.ts`) fails fast at startup if unset in production, rather than silently signing every access token with the hardcoded dev fallback string. Dev/test are unaffected — the fallback still applies there.
- Passwords and OTP codes are bcrypt-hashed. Refresh tokens are SHA-256-hashed (they're already high-entropy opaque strings, not low-entropy secrets — no need for bcrypt there).
- Refresh tokens: HttpOnly cookie, one cookie **name per portal** (`patient_refresh_token`, `hospital_refresh_token`, `owner_refresh_token`) — cookies aren't port-scoped, so a shared name would let one portal's login silently overwrite another's session in the same browser. Rotated on every refresh. Bound to the portal they were issued for.
- **Refresh tokens and OTPs live embedded on `User`** (`refreshTokens[]`, `registerOtp`, `resetOtp` in `models/user.model.ts`), not in separate collections — there is no `RefreshTokenModel`/`OtpModel` anymore. `registerOtp`/`resetOtp` are single overwritable slots (a new request just replaces the old one) and are cleared immediately on successful verification — and also discarded outright after `OTP_MAX_ATTEMPTS` wrong guesses (`utils/otp.ts`), which is what makes the 10-minute expiry meaningful given nothing else in the stack rate-limits attempts. Codes come from `crypto.randomInt`, never `Math.random`: the same generator backs password reset, so a predictable one is an account-takeover path. **A failed attempt has to be persisted, so the OTP checks must not throw from inside `withVersionRetry`'s `mutate`** — a throw there skips the `save()` underneath it and the counter would silently never count; they return an outcome and the caller throws after the save (see `checkOtpCode`). They are not marked "used" and left to rot. **Never add a TTL index on either of these fields** — a TTL index deletes the *whole document* it's on when it fires, which for an embedded field on `User` means deleting the entire account. That's exactly why these aren't in their own collections with a TTL index anymore.
- **This embedding has a real concurrency cost — don't reintroduce it.** Because everything now lives on one `User` document, two requests for the same user can race to modify it. We hit this for real (a `VersionError` from Mongoose's optimistic-concurrency check, thrown by concurrent `/api/auth/refresh` calls — plausible any time, guaranteed under React StrictMode's double effect-invocation in dev). The fix, in `domain/auth.service.ts`:
  - **High-frequency paths** (`issueTokens`/`login`/`refreshSession`/`logout`/`rememberSelectedHospital`) use atomic MongoDB update operators (`$push`/`$pull`/`$set` via `UserModel.updateOne`), never a fetch→mutate→`.save()` cycle. A read-then-write-with-retry is *not* sufficient here even though it prevents crashes — under a genuine burst, several requests can each read the same snapshot, each correctly compute "still under the cap," and all successfully save in sequence, exceeding the cap anyway. Verified: 8 truly concurrent logins for one user still cap at exactly 3 with atomic operators; the retry-based version let it reach 6.
  - **Low-frequency paths** (register/verify-OTP/forgot-password/reset-password) use `withVersionRetry` — fetch, mutate, save, and retry on `VersionError` with a fresh re-fetch. This is fine here because a user isn't realistically firing concurrent requests at these; it wouldn't be fine for login/refresh.
  - If you add a new field or flow that touches `User.refreshTokens` or any other frequently-written field, use an atomic operator, not `.save()`.
- **The `refreshTokens.tokenHash` unique index must stay a *partial* index — don't drop `partialFilterExpression`.** MongoDB indexes an empty array the same as a missing field: both produce a single `null` key in a multikey index. Without the partial filter (`{ "refreshTokens.0": { $exists: true } }`), the second user account that ever reaches zero refresh tokens (anyone who's logged out, or never logged in) collides with the first on that shared `null` key — this actually happened live, silently breaking `POST /api/auth/register` for everyone once a second such account existed, and wasn't caught until a full-project audit. The partial filter excludes empty/missing arrays from the index entirely, so any number of zero-token users can coexist; real tokens are still enforced unique. If you ever touch this index, keep the partial filter.
- Max 3 concurrent refresh tokens per `(userId, portal)` (`MAX_REFRESH_TOKENS_PER_PORTAL` in `domain/auth.service.ts::issueTokens`), FIFO-evicted on the next login past the cap. **Scoped per portal, never globally per user** — one account can hold separate patient/hospital/owner sessions at once, so a global cap would let a new device login on one portal silently sign the user out of an unrelated portal. If you ever add a "log out other devices" feature, keep it scoped the same way.
- Portal isolation is strict: a session authenticated through one portal must never expose data, roles, or endpoints belonging to another portal, even for a user who holds multiple roles. Enforce with `requirePortal(...)`, not just frontend routing.
- **Permissions fail closed, always.** `requirePermission(...)` (`middleware/permission.middleware.ts`) resolves permissions fresh from the database on every request via `domain/permission.service.ts` — never cached, never read from the JWT. A missing/inactive `HospitalMembership`, a missing/inactive `AccessRole`, an `AccessRole` belonging to a different hospital than the current context, or any invalid permission data all resolve to *zero* permissions — never to unrestricted access. This means a permission change in MongoDB takes effect on the staff member's very next request, with no logout/login/refresh needed — that's a feature, not a caching bug to "fix" later.
- Only permission strings from the catalogue (`config/permissions.ts`) may ever be stored on an `AccessRole` — validated on creation, never arbitrary strings. `PATCH /api/hospital/access-roles/:id` validates the same way on edit.
- **`AccessRole` deletion is a hard delete, by explicit decision** (`domain/accessRole.service.ts::deleteAccessRole`) — not the soft-deactivate (`isActive`) pattern used elsewhere in this file. It's blocked with `409` while any *active* `HospitalMembership` still points at it, so it can't silently orphan a currently-in-use role. If you're tempted to add a separate deactivate/reactivate toggle later, check whether hard-delete-with-a-block already covers the need before building both.
- `HospitalMembership.role: "admin" | "staff"` and the dynamic `AccessRole`/permission system are two separate mechanisms, but **not non-overlapping**: `role: "admin"` gates hospital-*management* actions directly (creating/listing AccessRoles, reviewing access requests) — an administrator doesn't need an `AccessRole` for those. `AccessRole` permissions gate staff clinical/functional actions via `requirePermission`, resolved by `domain/permission.service.ts::resolvePermissions`. **`resolvePermissions` also returns every permission in the catalogue for `role: "admin"`**, current and future, without the admin ever needing an `AccessRole` assigned — a deliberate product decision that the hospital administrator has full access to everything a hospital account can do, while every other staff member is limited to whatever `AccessRole` they're assigned. This is the one intentional overlap between the two systems; still fails closed underneath (a `removed`/`disabled` admin membership, or a disabled hospital, resolves to no permissions same as anyone else — see the function's own comments). If you add a new `requirePermission`-gated route or a new `resolveCanX`-style frontend-facing boolean (`canManageStaff`, `canViewPatients`), you don't need to special-case admin into it — it's already covered at the `resolvePermissions` level, one place, not per-feature.
- Never hardcode a clinical job title (Doctor/Nurse/Cardiologist/etc.) into authorization logic anywhere. Those are just example `AccessRole.name` values a hospital admin might choose — the app never branches on them.
- Never expose secrets to the frontend. `BREVO_API_KEY` and friends stay in `backend/.env` (gitignored) — never in `.env.example`, never in frontend code.
- **Hospital-scoped lookups: filter by hospital in the query, don't fetch-then-check.** When an admin acts on something by id (an access request, later a role edit, etc.), look it up as `findOne({ _id, hospitalId: req.hospitalId })`, not `findById(id)` followed by an `if (doc.hospitalId !== req.hospitalId)` check. The query-level filter means a cross-hospital id simply isn't found (`404`) rather than being found-then-rejected — smaller surface for a forgotten check to leak existence/data across hospitals.
- **State machines are one-way unless a transition is explicitly designed.** `HospitalMembership.status` (`pending → active | rejected`, `active → removed`, `pending → cancelled`) only ever moves forward from `pending`; `active` and `rejected` are terminal until a real "re-request" or "change role" feature is deliberately built (see PHASES.md) — don't let an approve/reject handler silently re-fire on an already-decided record. `removed` (staff removal) and `cancelled` (the requester withdrew their own pending request) are the two deliberately-designed one-way exceptions — both non-terminal: `requestAccess` lets either kind submit a fresh request, reusing the same document and resetting it to `pending` (`domain/accessRequest.service.ts::REREQUESTABLE_STATUSES`). `rejected` stays terminal as before; only those two reopen. **`disabled` is the one bidirectional pair**: `active ⇄ disabled` via `domain/staff.service.ts::disableStaffMember`/`enableStaffMember` — a reversible, temporary suspension, distinct from `removed` (which represents leaving; rejoining needs a fresh request). Disabling leaves the membership row and its `accessRoleId` completely untouched; every place that already filters on `status: "active"` (`resolvePermissions`, `verifyActiveMembership`, `listActiveMemberships`) is what actually cuts off a disabled member's access and permissions — don't add a separate "is this membership disabled" check anywhere, the existing `status: "active"` filters already cover it for free.
- **Staff removal/disable authorization is broader than plain admin-gating, with a peer-protection rule.** `domain/staff.service.ts::removeStaffMember` and `disableStaffMember` both allow either a hospital `admin`, or a staff member whose *current* `AccessRole` includes the `staff.manage` permission (resolved fresh via `resolvePermissions`, never cached — same as any other permission check, exposed to the frontend as `HospitalContext.canManageStaff` for display/gating only). A `staff.manage` holder can remove/disable other staff but **not** another `staff.manage` holder (peers can't act on each other) and never an admin — the target's `role` is checked to be `"staff"`, never `"admin"`, before anything else, so the hospital administrator can never be removed or disabled through these endpoints regardless of who's asking. Self-removal/self-disable is blocked outright. `enableStaffMember` is deliberately **not** peer-protected — restoring access isn't the kind of action that needs guarding against peers, and a disabled person can't call any staff-management endpoint themselves anyway (their own membership isn't `"active"`, so `assertCanManageStaff` already rejects them). If you extend this (e.g. a "manager" concept elsewhere), keep the peer-protection and admin-immunity rules on the destructive/suspending actions — don't let one manager silently remove or disable another, or anyone act on the admin.
- **Adding staff directly (`staff.service.ts::addStaffDirectly`) and reassigning a staff member's role (`updateStaffRole`) are both admin-only** — `assertHospitalAdmin`, not the broader `assertCanManageStaff` a `staff.manage` holder satisfies for listing/removing/disabling. A `staff.manage` holder was never able to approve a pending request either, so shouldn't gain the power to create one directly or reassign roles — keep create/approve/role-reassignment admin-only if you touch this again. `updateStaffRole` specifically mirrors `accessRole.service.ts`'s admin-only gating (`assertHospitalAdmin`, same as create/edit/delete role) rather than `assertCanManageStaff`, since it's an AccessRole-management action, not a staff-roster one — and a `staff.manage` holder can't even list AccessRoles today (`listAccessRoles` is admin-only), so the frontend couldn't offer role-reassignment to them regardless. `addStaffDirectly` mirrors `hospital.service.ts::createHospitalWithAdmin`'s exact pattern for a brand-new account (generate + hash a temp password, email it once via `utils/email.ts::sendStaffWelcomeEmail`, `isVerified: true`); an existing account is left alone except gaining `"hospital"` in `User.roles` if missing — required for `login()` to ever admit them to the Hospital Portal at all, since `login` checks `roles.includes(portal)`. **Every eligibility check runs before any write**: the role grant used to happen first, so a rejected add still permanently widened what that account could log in to. For the same reason, if the membership write fails after a brand-new account was created, that account is deleted again — otherwise it would survive holding a temporary password that was never emailed (the email only goes out once the membership sticks), and a retry would take the existing-account branch and never send one.
- **Cancelling a request is user-scoped, not hospital-scoped.** `accessRequest.service.ts::cancelRequest` looks the membership up by `{ _id, userId }`, not `{ _id, hospitalId }` — the requester may have no hospital context selected yet (that's the whole point of a pending request), so there's no `req.hospitalId` to scope by. Don't add a hospital-context requirement to this route.
- A defensive check can be provably unreachable given other constraints already in place (e.g. the self-approval check in `accessRequest.service.ts` — unreachable because the unique `(userId, hospitalId)` index already rules out someone being simultaneously an active admin and a separate pending requester in the same hospital). Keep such checks as defense-in-depth, but don't invent a test that has to violate a real constraint just to exercise it — say so plainly instead.
- **`Hospital.isActive` (Owner-only, `domain/hospital.service.ts::disableHospital`/`enableHospital`) is the hospital-level equivalent of `HospitalMembership`'s `disabled` status** — a reversible pause, not a delete. Nothing about the hospital's staff/admin memberships or AccessRoles changes when it's disabled; what actually cuts off access is that **every** hospital-access check additionally requires it: `verifyActiveMembership`, `getCurrentHospitalContext`, `resolvePermissions`, `assertHospitalAdmin` (`accessRole.service.ts`), `assertCanManageStaff` (`staff.service.ts`), and `requestAccess` (`accessRequest.service.ts`) all separately query `HospitalModel` and fail closed (403, or `[]` for `resolvePermissions`) when `isActive` is false — this blocks an already-issued session mid-lifetime, not just a fresh `select`. If you add a new hospital-scoped check, add the same `isActive` guard rather than assuming an earlier check in the call chain already covered it — there's no single shared choke point, each of these five does its own lookup. `listActiveMemberships` (Hospital Portal's "Your hospitals") and `listRequestableHospitals` (the staff-facing "browse hospitals to request access to" list) both filter disabled hospitals out entirely; `listHospitals` (Owner's own list, `GET /api/owner/hospitals`) deliberately does **not** filter — the Owner needs to see a disabled hospital in order to re-enable (or delete) it.
- **Deleting a hospital (`deleteHospital`) is a real hard delete, unlike everything else hospital-scoped** — cascades to permanently remove every `AccessRole` and `HospitalMembership` (staff *and* admin) tied to it, then the `Hospital` document itself. This was a deliberate choice, confirmed with the user, over blocking deletion while any membership exists (that pattern, used for `AccessRole`, doesn't work here — there's no way to ever remove a hospital's *admin* membership through any other endpoint, so "blocked while non-empty" would make delete nearly unusable). It deliberately does **not** touch the `User` accounts those memberships pointed to — a person might hold other portals' roles (or, per the one-hospital rule below, a membership at a different hospital entirely), so only their access to *this* hospital disappears, not their account. If you extend this later (e.g. deleting a `User` outright elsewhere), don't assume this function's cascade pattern generalizes — it was scoped specifically to "everything meaningless without this hospital," not "everything this hospital ever touched."
- **One account = one hospital (Phase 1 rule).** A `User` may hold at most one *live* `HospitalMembership` at a time — `status` of `pending`, `active`, or `disabled`. `rejected`, `removed`, and `cancelled` are non-live: reaching any of them frees the account to request or be directly added to *any* hospital again, not just the one it left (a genuine behavior change from before this rule — removal used to only reopen the *same* hospital via `REREQUESTABLE_STATUSES`). Enforced in two layers: an application-level check (`accessRequest.service.ts::assertNoOtherLiveMembership`, called from `requestAccess`, defensively again in `approveRequest`, and inlined equivalently in `staff.service.ts::addStaffDirectly`) that gives a clean `409`, and a database-level partial unique index on `HospitalMembership.userId` (`models/hospitalMembership.model.ts`) as the real backstop against any future code path that forgets the check. **The index is on a denormalized `holdsHospitalSlot` boolean, not `status` directly** — MongoDB partial-index filters only support equality/`$exists`/comparison, not `$in`/`$or`, so "status is one of three values" can't be expressed as the filter itself. `holdsHospitalSlot` is derived automatically by a `pre("save")` hook on the schema, never set by application code — every status-changing path for `HospitalMembership` in this codebase uses `document.save()` (never `updateOne`), so the hook always fires; if you ever add an atomic-update path for `HospitalMembership` (unlikely — it doesn't have `User.refreshTokens`' concurrency profile), you'd need to set `holdsHospitalSlot` there too. Don't drop this index or "clean up" the field thinking it's redundant with `status` — same category of mistake as dropping the `refreshTokens.tokenHash` partial filter elsewhere in this file. The error message shown to a *requester* names their own current hospital (their own data, safe to reveal); the error shown to an *admin* attempting `addStaffDirectly` on someone who belongs elsewhere is generic and never names the other hospital (hospital isolation — it's not that admin's data to see). This phase deliberately does not build a multi-account "one person, several hospital accounts, with a switcher" experience — see PRD.md's Future scope — so don't reintroduce hospital-switching UI/logic beyond the existing single-membership `POST /api/hospital/select`.

- **Patient ↔ doctor data-sharing consent (`PatientConsent`, `domain/patientConsent.service.ts`) is a relationship gateway, not the medical data itself** — the data it gates (vitals, sepsis scores, alerts) lives in its own models, see "Vitals, sepsis scoring & alerts" below. Same one-document-per-pair shape as `HospitalMembership` (unique on `(patientId, doctorId)`), and the same non-terminal-revocation pattern: `status: "revoked"` isn't terminal, granting again reuses the same document and resets it to `"active"`.
  - **Edit is patient-only, enforced by route existence, not a role check.** There is no hospital-side edit endpoint at all — `PATCH /api/patient/consents/:id` only exists under `routes/patient.routes.ts` (`requirePortal("patient")`), so a doctor's Hospital Portal session can't reach it regardless of any in-handler check. If you ever add a doctor-initiated flow (see PRD.md's Future scope), don't let it grow into the ability to change `dataCategories` — that stays the patient's alone.
  - **Revoke is symmetric and never permission-gated on the doctor's side** — giving up access you hold is never a privilege concern, unlike *seeing* it (below). Both `POST /api/patient/consents/:id/revoke` and `POST /api/hospital/patient-consents/:id/revoke` share one domain function (`revokeGrant`), query-scoped to `{ _id, $or: [{patientId: actor}, {doctorId: actor}] }` — a grant belonging to neither the caller's patient side nor doctor side simply isn't found, same "filter in the query" convention as everywhere else.
  - **`lookupDoctorByEmail` never confirms whether an email exists in some other capacity** — the exact same generic `404` whether the email doesn't exist at all, belongs to a non-hospital account, or belongs to a hospital account with no currently-active `HospitalMembership`. Same anti-enumeration principle as `auth.service.ts::forgotPassword`'s "always respond the same way" — don't add a more specific error message here even if it seems more helpful.
  - **`patient.view` is the first permission from the RBAC catalogue to actually gate something** — it existed from the original RBAC foundation onward but nothing used it until `GET /api/hospital/patient-consents`. `HospitalContext.canViewPatients` (from `getCurrentHospitalContext`/`verifyActiveMembership`) mirrors `canManageStaff`'s shape for the frontend, and — like `canManageStaff` — is `true` for `role: "admin"` automatically, via `resolvePermissions`' own admin short-circuit (see the `HospitalMembership.role` vs. `AccessRole` bullet above) rather than a special case in `resolveCanViewPatients` itself; every other staff member only sees granted patients if their own `AccessRole` actually includes `patient.view`.
  - **`User.specialization`** is optional at the schema level (same "not every creation path needs it" precedent as `phone`), free text, and **must never become a fixed clinical-title enum** — same standing rule as never hardcoding "Doctor"/"Nurse"/"Cardiologist" into authorization logic, just applied to a self-description field instead. It's returned on `GET /me`/login for any portal (not gated by `req.portal` the way `hospital` context is) since it's descriptive text, not access-sensitive.
  - **`config/dataCategories.ts` is a separate catalogue from `config/permissions.ts`**, validated the same way (fixed array, `isValidDataCategory`, never arbitrary strings) but a different axis — permissions gate what a staff member's `AccessRole` can *do* in a hospital; data categories gate what a *patient* is willing to *share*, independent of any hospital. Don't merge them even though the validation pattern is identical.
  - **Clinical reads never trust a `PatientConsent` grant alone** — every vitals/score/alert read also re-checks the doctor's *current* permission (fresh via `requirePermission`), the same dual-layer check `listGrantedToMe` does for visibility. A grant naming a doctor who's since lost hospital access, or the specific clinical permission, must not translate into data access. See the next section.

- **Patient profile (`User.dateOfBirth`, `gender`, `bloodType`, `guardianPhone`).** Date of birth, not an age (it never goes stale; stored as UTC midnight, age computed on UTC date parts). All optional at the schema level (same precedent as `phone`): hospital/owner accounts never have them. The Patient Portal requires DOB, gender and blood type on first login (`isPatientProfileComplete`) and lets the patient edit all four (`PATCH /api/patient/profile`, `auth.service.ts::updatePatientProfile`, rules checked *before* `withVersionRetry`'s mutate). `gender` is `male`/`female`/`other`. `bloodType` includes `"unknown"` on purpose — the field is required, and a patient who doesn't know theirs must never be pushed into guessing a value a doctor will read; don't remove that option. `guardianPhone` is optional (7–15 digits; empty clears it). Doctors see them only through reads that are already consent- and permission-gated (`/patients/:id/vitals`, `/patient-consents`, `/alerts`) — never add them to `lookupDoctor`-style or unauthenticated responses.
- **Prescription upload is a frontend placeholder too** (Patient `/prescription`: `src/components/prescription/*`, `src/lib/prescription.ts`). The image is previewed from a local object URL and never uploaded, stored or read; "Analyze Prescription" is disabled (`PRESCRIPTION_ANALYSIS_AVAILABLE = false`) and the "Extracted Prescription" table only ever shows its placeholder row. `analyzePrescription()` is the single seam for the future pipeline (image → backend upload → OCR/handwriting model → extracted medicines) and deliberately throws today — implement it there, keep unreadable fields as `null` (shown "—", never guessed), and keep the original image on screen beside the result so it can be checked against the handwriting.
- **Chest X-ray is a frontend placeholder** (`ChestXrayUpload`, Patient `/xray` page + a card on the doctor's patient page): the image is previewed from a local object URL and is never uploaded, stored or analysed — no endpoint, no model. The card says so. When a real X-ray model is built, it needs its own storage, consent category and permission design first; don't bolt an upload onto this component.

- **Vitals, sepsis scoring & alerts** (`domain/vitals.service.ts`, `domain/inference.service.ts`, `domain/alert.service.ts`, `ml-service/`). The model is a **research prototype** (PhysioNet/CinC 2019), not a diagnostic tool.
  - **The model runs only in `ml-service/`**, never re-implemented in TypeScript: its preprocessing (range cleaning, forward-fill, median imputation, scaling, calibration, per-model thresholds) is the source of truth, and a TypeScript copy is the likeliest way to get a subtly wrong probability. `ml-service/sepsis_core.py` is generated by the model's notebook — don't hand-edit it. The service has no auth: it listens on `127.0.0.1` only, `ML_SERVICE_URL` is backend-only config, and no frontend ever calls it.
  - **Send the whole history, as elapsed hours, one row per hour** (`inference.service.ts::buildHistory`). Not just the last 6 hours: the network uses 6, but the forward-fill that fills a gap in them reaches further back (the model's own docs: "streaming equals batch only with full history"). `hour` is whole hours since the first reading, never a row index — the model treats missing hours as unmeasured, so renumbering would erase real gaps — and same-hour readings are merged, since a duplicate hour is a 422. Never send names, emails or ids.
  - **Store vitals exactly as captured, nulls included** — never pre-fill medians; the model imputes and reports what it filled in `warning`.
  - **Alerts come from the model's `risk_level`, on `HIGH` only** — never from a probability threshold picked in CarePulse (thresholds are calibrated per model and move on retrain), and not on `ELEVATED` (54% of non-septic patients would be alerted). **One active alert per patient** is enforced by a partial unique index on `Alert.patientId` (`status: "active"`); `raiseAlertIfNoneActive` creates directly and swallows the duplicate-key error, which is the normal outcome for every HIGH hour after the first — don't replace it with a check-then-create (racy) or drop the partial filter.
  - **A failed score fails closed but never fails ingestion.** Model down / 5 s timeout / bad response → a `SepsisPrediction` with `status: "unavailable"`, logged without patient data; the reading is still saved and the request still `201`s. The UI shows `UNKNOWN` (`RiskBadge`), never `LOW` — absence of a score is not evidence of low risk.
  - **The gate is `vitals.continuous` + the route's permission.** `GET /api/hospital/patients/:id/vitals` (`vitals.view`), `GET /api/hospital/alerts` (`alerts.view`), `POST /api/hospital/alerts/:id/acknowledge` (`alerts.acknowledge`), each with `requirePermission` **and** `patientConsent.service.ts::assertActiveConsent`/`consentedPatientIds` (query-scoped; no grant → `404`, the same as a nonexistent patient). This hourly model-driven feed is "continuous" vitals: a patient who shared only `vitals.occasional` has not shared it. `HospitalContext.canViewVitals`/`canViewAlerts`/`canAcknowledgeAlerts` are display only.
  - **`recordedAt` comes from the client** (readings aren't always sent when taken, and the replay sends a whole stay at once), bounded in `recordVitals` to the last 14 days and at most 5 minutes ahead. Vitals are patient-recorded only for now — a staff/device write path would need its own permission (e.g. `vitals.record`), not a reuse of `vitals.view`.
  - **Time a score by its reading, never by when it was written.** `SepsisPrediction.readingId` is the reading the score is *as of* — the patient's newest reading when it was scored — not the reading whose arrival triggered scoring (a late, older reading still gets the latest hour scored). Display reading `recordedAt`, not `createdAt`: a batch or replay writes hours of scores within seconds, so a write time looks current when the reading isn't. An alert stays active while the risk moves, so `listAlerts` returns the triggering score *and* the patient's `current` (latest) score, each with its reading time, and the Alerts page shows both — never the trigger alone as if it were now. (Found for real: a replayed stay's alert read "HIGH 6.3%, raised 22:25" while the 22:25 reading was ELEVATED 3.7%; the HIGH was from a reading 42 hours earlier.)
  - **The ML prediction summary describes the model truthfully** (`VitalsHistory.tsx`): "Sepsis Early-Warning (SSL-LSTM)" and a horizon of "up to 6 h before sepsis onset" (the PhysioNet 2019 label turns on 6 h before onset). A request to show it as a generic "Physiological Deterioration Model" with a "3 hours" horizon was declined in favour of this, by the user's own choice — don't relabel the model as something it wasn't trained to predict.
  - **Every surface that shows a score or alert shows `ResearchDisclaimer`** (`@carepulse/ui`), and leads with the level, not the percentage — calibrated probabilities are small (HIGH starts around 5.7%), so the number alone reads as reassuring.

## Preserve working systems

Authentication, portal isolation, refresh-token rotation, hospital-switching, and now the RBAC permission-resolution foundation are built and tested (see `backend/tests/`). Don't rewrite them "while you're in there" — extend them. If a new feature seems to require changing this core, stop and confirm that's actually necessary first.

## Frontends

Three separate TanStack Start apps (`patient-frontend` 3001, `hospital-frontend` 3002, `owner-frontend` 3003) — do not merge them into one app. The repo is an **npm workspaces monorepo** (root `package.json`, one root `package-lock.json`; `backend/` stays outside it with its own lockfile). **Code that is the same in every portal lives once, in `packages/`**; each app keeps only what is genuinely portal-specific (routes/pages, `nav.ts`, `src/lib/api.ts` portal registration, `src/lib/queries.ts`, its `<Portal>Layout`, and the Hospital Portal's `useMe`/access gate/`components/access/*`):
  - `@carepulse/api` (`packages/api`) — types (`@carepulse/api/types`) + the API client (`packages/api/src/api.ts`).
  - `@carepulse/ui` (`packages/ui`) — the UI primitives (incl. `RiskBadge`, `ResearchDisclaimer`), `Toast`, `Skeleton`, `RouteError`, the `cp-*` token stylesheet (`@carepulse/ui/styles.css`) and fonts (`@carepulse/ui/fonts`).
  - `@carepulse/portal` (`packages/portal`) — `Header`, `Sidebar`, `AccountMenu`, `VitalsHistory` (ML prediction summary + trend charts + readings table, rendered by both Patient and Hospital; the charts are `VitalsTrends`, recharts, lazy-loaded), `ChestXrayUpload`, `formatDemographics`/`ageInYears`, `useSession`, `useAuthSync`/`broadcastAuth`, `prefetch`, `createQueryClient()` and `routerDefaults`.

  Packages ship TypeScript source (their `exports` point at `src/*.ts`, no build step); each app's `tsc` type-checks them as part of its own program, and `npm run lint:packages` lints them. Don't copy a shared component back into an app to tweak it — change it in the package, or keep the portal-specific part in the app. This replaced the earlier "duplicate per app on purpose" rule, by explicit decision, once 76% of the three apps' files were byte-identical copies. The backend URL comes from `VITE_API_URL` in each app's `.env.local`. Keep the access token in memory only (never localStorage); each app calls `restoreSession()` on load to trade the refresh cookie for a new access token.

- **All three apps run TanStack Start in SPA mode (`tanstackStart({ spa: { enabled: true } })` in `vite.config.ts`) — keep it that way.** The access token is a module-level variable in `packages/api/src/api.ts` and the refresh cookie goes from the browser straight to the backend; neither exists on a render server. With SSR on, route loaders would run server-side with no session, and a module variable on a server is shared by every visitor's request. Likewise, don't call the backend from `createServerFn` or server routes — Express is the only backend. Fetch in components (or client-side loaders) as the pages already do.
- Routes are file-based under `src/routes/` (`src/routeTree.gen.ts` is generated by the Vite plugin on `dev`/`build` — commit it, never hand-edit it). Navigation is `@tanstack/react-router`'s `<Link to>` / `useNavigate()` / `useLocation()`; there is no `next/*` import anywhere. `<TanStackDevtools />` (Router panel) in `__root.tsx` is dev-only — the `devtools()` Vite plugin strips it from production builds; keep that plugin first in `plugins`. **Keep its `consolePiping` disabled**: it forwards browser logs to the terminal *and* terminal logs back to the browser, so one client `console.error` echoes between them forever (it flooded the dev server log to 5 MB in seconds and got the e2e run killed).
- **Data fetching: TanStack Query, in every page and portal layout** — no page fetches in a `useEffect` anymore. The `QueryClient` comes from `createQueryClient()` (`@carepulse/portal`), is created per router in each app's `src/router.tsx`, and provided via the router's `Wrap`; `routerDefaults` holds the shared router options below. Rules that exist for security/correctness reasons:
  - **Expired access tokens renew themselves.** `apiFetch` (`packages/api/src/api.ts`) retries a request once after a 401, having first called `restoreSession()` for the portal the app registered via `setRefreshPortal` in its `src/lib/api.ts` — through the same in-flight dedup, so a burst of 401s causes exactly one refresh. Login/refresh/logout 401s are never retried. If the refresh fails (cookie gone/revoked), `onSessionLost` (wired in `createQueryClient()`) sets the `["session"]` query to `null`, so the app shows its logged-out state, not an error.
  - Because of that, `useSession()` is restored **once per page load** and cached (`staleTime: Infinity`); login writes the new user into `["session"]` (`setQueryData`), logout clears the cache. `useMe()` (Hospital Portal — role/`canManageStaff`/`canViewPatients`) is the opposite: `staleTime: 0`, `gcTime: 0`, and pending until **this mount's own** fetch *succeeds* (`isFetchedAfterMount && isSuccess` — a failed refetch keeps old `data` beside the error, which must never be rendered). A client-side navigation never renders permission flags an earlier page cached. Verified: revoking `patient.view` server-side then clicking to `/patients` issues `/me` → no patient-list request. Don't "optimize" `useMe` into rendering cached data first.
  - `retry: false` globally (401 is handled by `apiFetch`; 403/404 can't be fixed by retrying). `refetchOnWindowFocus` is on (the default) now that expired tokens self-heal.
  - `HospitalLayout`'s access gate is one `["hospitalAccess"]` query with `staleTime: 0`/`gcTime: 0` (re-resolved on every portal mount). `HospitalAccessGate`'s optimistic "Permission sent" override is stamped with the gate query's `dataUpdatedAt` (passed as `resolvedAt`) and stops applying on **any** newer resolution — `dataUpdatedAt` moves even when a re-check returns identical data, which is exactly the case (a request that didn't persist) that used to pin users on "Permission sent". Don't key it on the `myRequests` array identity instead.
  - Every `<Portal>Layout`'s `handleLogout` does `await navigate({ to: "/login" })` **then** `queryClient.clear()` in its `finally` — navigating first means nothing still mounted refetches into the cleared cache, and clearing means the next account on the same browser never sees this one's data.
  - **Cross-tab sync** (`packages/portal/src/authSync.ts`): `handleLogout` ends with `broadcastAuth("logout")` and the login page sends `broadcastAuth("login")`; each `<Portal>Layout` runs `useAuthSync()`, which on "logout" does the same navigate-then-clear (no second backend call — the shared refresh cookie is already revoked) and on "login" invalidates `["session"]`. Each portal is its own origin, so the `BroadcastChannel` never crosses portals. Broadcast only after this tab has left the layout, or the sending tab would react to its own message.
  - **Hover preloading + freshness.** Routes are code-split (TanStack Start always does this — it doesn't even expose `autoCodeSplitting` as an option). Components only some users open on demand are `React.lazy` chunks too — `AddStaffModal`/`ManageRolesPanel` (fetched on hover/focus of the button that opens them) and `HospitalAccessGate` (active staff never download it). The main bundle is ~106 KB gzip of framework code (react-dom, router, query, seroval); app code in it is ~6 KB, so look for page-specific imports there before assuming it can shrink. The router uses `defaultPreload: "intent"` with a 350 ms `defaultPreloadDelay`: hovering/focusing a link that long loads the route's code and runs its `loader`, which prefetches that page's data via `prefetch()` (`@carepulse/portal`) using the query definitions in the app's `src/lib/queries.ts` (so loader and page share one key). The global `staleTime` is 20 s, so a click within that window reuses the prefetched data. **`session`, `me` and `hospitalAccess` explicitly override this back to `staleTime: 0`** — they're access-deciding and must be re-asked on every page mount; don't let the 20 s default reach them. `prefetch()` skips when there's no access token yet (fresh page load). Hospital loaders only prefetch lists the user's cached `hospitalAccess` context says they can load (`cachedHospitalContext`) — that only picks what to prefetch; pages still gate on fresh `useMe()`.
  - UI state worth keeping on reload/back/share goes in the URL via the route's `validateSearch` (plain function, optional keys so plain `<Link to>` still type-checks) — e.g. `/access?q=` for the staff search, updated with `navigate({ search, replace: true })` so typing doesn't add history entries.
  - **Optimistic updates only for reversible, low-stakes row actions**: hospital enable/disable and delete (Owner), staff enable/disable (Access), consent revoke (patient) and give-up (doctor) — `onMutate` snapshots + updates the cached list, `onError` restores it and shows `toast.error`, `onSettled` invalidates. **Staff removal, role reassignment and alert acknowledgement stay non-optimistic** (the modal/row waits for the server): removal can't be undone, and what role/permissions someone holds is the server's to confirm. Never apply an optimistic update to `session`, `me` or `hospitalAccess`.
  - Every route has `defaultErrorComponent` (`RouteError` in `@carepulse/ui` — "Something went wrong" + **Try again** → `router.invalidate()`) and `defaultPendingComponent` set in `routerDefaults`, so a render crash never leaves a blank page.
  - After a mutation, invalidate the affected query keys rather than hand-editing cached lists. `AddStaffModal`/`ManageRolesPanel` still call their own API functions and report back via callback props; the Access page's callbacks are just `invalidateQueries`.

`lucide-react` is a real dependency in all three frontends, used for decorative icon accents (`IconBadge` next to a `Card`/section title, Sidebar nav items, the Header/auth-page brand lockup) — never as the sole affordance for an action; every icon sits beside a real text label. See DESIGN.md for the full adopted palette — an exact, named CarePulse token system (`cp-*` Tailwind v4 `@theme` tokens, e.g. `cp-primary`/`cp-text`/`cp-border`, each with a real light *and* dark value) plus DM Sans/Space Mono typography, superseding the earlier generic-Tailwind teal pass. **Use only the named `cp-*` tokens for anything the palette covers — never a raw `slate-*`/`teal-*` class, and never invent a shade that isn't one of the given values.** The palette has been swapped twice now (indigo → teal → the exact token system); if it changes again, it'll go through the same file-by-file pass documented in DESIGN.md.

- **`restoreSession()` (`packages/api/src/api.ts`) deduplicates concurrent calls** via a module-level in-flight promise (called on page load by `useSession`, and by `apiFetch` on any 401). The refresh token rotates on every use, so two callers presenting the same cookie at once would otherwise race (first rotates it, second's rotation then 401s because that token is already gone) — this happened for real under React Strict Mode's double effect-invocation in dev. Because of this dedup, it's safe for more than one component (e.g. a portal layout *and* a page) to call `restoreSession()` on the same load — only one actual network request goes out. Don't remove this guard, and don't add a second, separate session-restore code path that bypasses it.
- **`handleLogout` in every `<Portal>Layout` must always clear client-side state and redirect, even if the backend logout call fails.** `logout()` (`packages/api/src/api.ts`) already clears the in-memory access token in a `finally` regardless of success/failure — so a network error there still leaves the client with a dead token. Wrap the call in try/catch (empty catch is fine — logout has nothing meaningful to show the user on failure) with the redirect and `queryClient.clear()` in `finally` (see the TanStack Query bullet above), not just after an awaited call with no catch — otherwise a failed request leaves the shell rendering as authenticated with an unhandled promise rejection.
- **Styling: Tailwind CSS v4, in all three frontends.** Installed via `tailwindcss` + `@tailwindcss/vite` (in `vite.config.ts`), pulled in via `@import "tailwindcss";` in `packages/ui/src/styles.css`, which each app's one-line `src/styles.css` imports. **That stylesheet's `@source` lines must keep pointing at `packages/ui/src` and `packages/portal/src`** — Tailwind only auto-scans the app's own folder, so without them a class used only inside a shared component silently disappears from every app's CSS. No other styling system — no CSS Modules, no component library (MUI/Chakra/styled-components), no per-page CSS files. There's one small UI primitive set, `@carepulse/ui` (`Button`, `Card`, `TextField`, `Alert`, `Badge`, etc. — see DESIGN.md for the full list and conventions), shared by all three apps. Use the existing primitives before reaching for raw Tailwind classes on a new page; add a new primitive only once a second real page needs the same pattern.
- **Application shell (Header/Sidebar/`<Portal>Layout`) — Tailwind, not plain CSS.** Each portal's protected routes live under `src/routes/_portal/`, a pathless layout route (the `_` prefix means it's not a URL segment — doesn't change any path) whose `src/routes/_portal.tsx` wraps its `<Outlet />` in that portal's `<Portal>Layout` (`PatientLayout`/`HospitalLayout`/`OwnerLayout`); `/login`, `/register`, `/forgot-password` stay outside it and render bare, with no header/sidebar. All three portals now have a Sidebar — Patient gained one once it got a second real route (`/sharing`); a single-route portal simply didn't need one before that, not a permanent asymmetry. `PatientLayout`/`OwnerLayout` do their own lightweight session check purely to decide whether to show navigation chrome — they never gate or replace a page's own auth handling, so a logged-out page's existing "log in first" state renders exactly as it did before the shell existed. **`PatientLayout` adds one UX gate:** a logged-in patient with no `dateOfBirth` or `gender` sees `CompleteProfileGate` (header + logout, no sidebar, no page) until both are saved — a product requirement, not a security boundary; nothing server-side depends on those fields (the replay script, for one, records vitals regardless). **`HospitalLayout` is the one exception, deliberately**: it's also the real Hospital Portal access gate (see the security-boundaries section above) — it re-derives the session's current membership status fresh on every load and only renders the shell + `children` once it's `active`; anything else renders `HospitalAccessGate` instead of the page. Don't describe `HospitalLayout` as "presentation only" the way the other two still are. Nav items are config-driven (`components/layout/nav.ts` per app) and only list routes that actually exist — don't add nav links to unbuilt pages. `Header`/`Sidebar`/`AccountMenu` live once in `@carepulse/portal`; each `<Portal>Layout` stays in its own app and decides what goes in them. Global actions live in the shell, not the page — logout is only in the Header, application nav only in the Sidebar; don't re-add a duplicate logout button or nav link to a page's own content. **Hospital Portal only:** the Header's account menu (`AccountMenu.tsx`) is a second, separate nav surface for personal/account actions (Profile — now a real page, editing `specialization` — Settings, Log out) — the Sidebar stays scoped to hospital-application navigation only; see the "Account navigation vs. hospital navigation" section in DESIGN.md before adding anything to either one.
- **Frontend nav filtering is presentation only, never authorization.** A `<Portal>Layout` may hide a nav item based on what it already knows about the session (e.g. hospital admin vs. staff), but that's cosmetic — the backend's `requirePermission`/`requirePortal` checks are the only real boundary. Never infer or store fine-grained permissions on the frontend to decide what to show; only use signals the session response already legitimately exposes.

## Testing & manual verification

- `cd backend && npm test` runs the vitest suite (hits the real MongoDB Atlas dev database and the real Brevo API — that's intentional, not mocked). **Because it shares the dev database with real use, every test cleanup must be scoped to the accounts/hospitals that test created** (`{ email: { $in: cleanupUserEmails } }`, `{ hospitalId: { $in: cleanupHospitalIds } }`, …) — never a filter that matches other data. `patientConsent.test.ts` once deleted `{ patientId: { $exists: true } }`, i.e. every consent in the database, so each test run silently wiped all real patient–doctor sharing. The one exception is the sepsis model: `tests/vitals.test.ts` fakes `ml-service` with a `fetch` spy that passes every other URL (Brevo) through. The model itself is the `sepsis_ml_master` project's to test.
- `ml-service/`: `uv venv --python 3.11 .venv && uv pip install --python .venv/bin/python -r requirements.txt`, then `./start.sh` (see `ml-service/README.md`; `start.sh` points xgboost at torch's bundled `libomp` on macOS — don't "fix" that by installing a second libomp, two OpenMP runtimes in one process crash). Demo: `npm run replay:vitals` in `backend/` with `REPLAY_PATIENT_EMAIL`/`REPLAY_PATIENT_PASSWORD` set — replays held-out stay `p012210`, the only one of the six that reaches HIGH.
- `cd e2e && npm test` runs the Playwright suite against the three real frontends (it starts their dev servers, or reuses already-running ones locally) with the backend **faked in the browser** (`e2e/fakeBackend.ts`, per-portal fakes like `e2e/tests/hospital/backend.ts`) — no database, email or seeded account needed. The fakes model the real backend's contracts (401 on an expired token, a new token on `/refresh` — without invalidating tokens other tabs still hold, since a new JWT never revokes an older one; modelling "only the newest token works" made two tabs refreshing at once knock each other out and failed CI — hospital context only after `/select`, `patient.view` enforced with a 403); if you change one of those contracts in `backend/`, change the fake too. Specs cover the access gate, session renewal (exactly one refresh per 401 burst), the revoked-permission click, hover prefetch/20 s freshness, optimistic rollback, cross-tab logout, `?q=`, lazy chunks and the error screen. First run: `npx playwright install chromium`.
- CI (`.github/workflows/ci.yml`): typecheck + lint + build for each frontend, the e2e suite, and a backend typecheck on every push/PR. The backend test suite only runs via a manual `workflow_dispatch` with `backend-tests` checked, and needs repo secrets `MONGODB_URI`, `JWT_SECRET`, `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, `BREVO_SENDER_NAME` — never commit those values.
- When manually verifying a new flow, prefer exercising it through the real HTTP API end-to-end over writing throwaway seed scripts. If a temporary script is genuinely needed for testing, delete it afterward — don't leave it in the repo.
- Ports are fixed: backend `5001`, patient `3001`, hospital `3002`, owner `3003`, ml-service `8000` (localhost only). Don't change them without updating `ALLOWED_ORIGINS`/`.env` everywhere.
