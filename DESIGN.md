# CarePulse — Design Direction

**Status: UI system live, visual palette adopted from a reference mockup.** The color palette, corner radius/shadow scale, and iconography below are the real adopted look (**teal** accent, `lucide-react` icons, `Avatar`/`IconBadge` primitives) — not a placeholder. Dashboard/clinical content is still not designed (Phase 3+). What *is* decided and built is the full application UI: the shell (header/sidebar) and every existing page's actual content, using Tailwind CSS and a small shared primitive set. Treat everything below as real, not a skeleton — it was applied to every existing route in all three frontends and verified against a real build.

The palette has been swapped once already (indigo → teal, second reference mockup). If it changes again, follow this file's own "How to use this file if the palette changes again" section at the bottom rather than guessing.

## Current actual state

Tailwind CSS v4 is installed in all three frontends (`tailwindcss`, `@tailwindcss/postcss`, wired via `postcss.config.mjs` and `@import "tailwindcss";` in `app/globals.css`). Every page — auth pages, the portal shell, and every protected page's content — is styled with Tailwind utility classes plus the shared primitives in `components/ui/`. There is no other styling system: no CSS Modules, no plain per-page CSS files, no component library. `components/layout/layout.css` (the pre-Tailwind shell CSS) has been deleted; the shell is Tailwind classes now too.

## UI primitives — `components/ui/` (Live, duplicated per app)

One small set of presentational components, written once and copied into all three frontends (not pulled into `shared/`, which stays scoped to types + the API client per CLAUDE.md). Import from the barrel: `import { Button, Card, ... } from "@/components/ui"`.

| Component | Purpose |
|---|---|
| `PageContainer` | The one page-width wrapper (`max-w-3xl`, responsive padding) — every page's top-level element. |
| `PageHeader` | `<h1>` + optional description, used once per page. |
| `SectionHeading` | Smaller `<h2>` + optional description, for grouping within a page (rarely needed once `Card` already has a `title`). |
| `Card` | Bordered, shadowed surface (`rounded-xl`, `shadow-sm`) with optional `title`/`description`/`icon`/`iconTone`/`children` (children is optional — a header-only card is legitimate for a non-actionable summary, e.g. Owner home's "Hospitals" pointer card); the base container for every form and list. `icon` (a `lucide-react` `LucideIcon`) renders an `IconBadge` next to the title when both are present — omit it when a card has no title, or when nothing in the icon set actually matches the section. `iconTone` forwards to `IconBadge`'s `tone` (default `teal`); pass `"neutral"` to deliberately deprioritize a card next to a primary one (e.g. a "System" status card beside "Your session"). |
| `Avatar` | Circle with initials, background tint deterministically hashed from `name` (`size`: `sm`/`md`/`lg`, `lg` = 48px for a page-level identity card). Purely decorative — never conveys meaning the way `Badge`'s tone does. Used in the account menu trigger, next to every person-row (staff list, pending-request list, hospital-switcher rows), and the Patient home session card. |
| `IconBadge` | Small colour-tinted rounded-square wrapping one `lucide-react` icon (`tone`: `teal`/`neutral`/`blue`/`amber`/`violet`, default `teal`). Used before a `Card`/section title and for Sidebar nav items — decorative only, never the sole affordance for an action; the text label is always right next to it. |
| `Label` / `Input` / `Select` | Bare styled form primitives — used directly when a composed `TextField` doesn't fit (e.g. a search box). |
| `TextField` | Label + Input + error/hint, id/`htmlFor` wired automatically via `useId()`. The default way to build a form field. |
| `Stepper` | Numbered progress indicator for short, linear multi-step flows (`labels: string[]`, `currentIndex`) — completed steps show a ✓, connecting lines fill in teal as you progress. Presentational only; the owning page decides what a "step" means. Used by Patient/Hospital `/register`. Owner has no multi-step flow, so it isn't copied there. |
| `Checkbox` | Styled checkbox + associated label (used for `AccessRole` permissions). |
| `Button` | One button for every case — `variant`: `primary` (default action) / `secondary` (neutral, e.g. "Switch hospital", "Log out") / `destructive` (full-weight, reserved for a confirmation step's final button, e.g. the Remove-staff confirm `Modal`) / `destructive-subtle` (low-emphasis tinted red, for a destructive action inline in a list row, e.g. "Remove"/"Reject"/"Delete" row buttons) / `ghost` (low-emphasis, e.g. sidebar collapse). |
| `Badge` + `toneForStatus(status)` | Status pill with a leading colored dot (`pending`/`active`/`rejected`/`admin` → tone) — display only, mirrors backend strings verbatim, never used for an access decision. `active`/`success` stays green (unchanged by the teal swap — semantic colors are deliberately fixed, see below); `admin`/`info` is the one tone that follows the accent (teal). |
| `Alert` | Replaces the old `<p style={{color:"red"}}>`/green pattern — `variant`: `error` (`role="alert"`) / `success` / `info`, each with a leading `lucide-react` icon (`alert-circle` / `check-circle-2` / `info`) matching the variant's color. |
| `EmptyState` | Centered message (+ optional action) for an empty list — replaces bare "No X yet." text. |
| `LoadingState` | Centered spinner + label — the one loading indicator, used both for full-page and section-level loading. |
| `Divider` | Plain styled `<hr>`. |
| `Modal` | Overlay dialog (`role="dialog"`, closes on Escape/overlay click/✕). Hospital Portal (`AddStaffModal`, the remove-staff confirmation) and now Owner Portal too (the delete-hospital confirmation, see below) — not yet copied to Patient since nothing there needs it. Role management (`ManageRolesPanel`) deliberately does **not** use `Modal` — see the Staff management section below. |

**Keep this list minimal.** Add a new primitive only once a second real page needs the same pattern — don't build ahead of actual usage.

## Color & typography conventions

Adopted from a second reference (a full design-handoff package: hex values + Tailwind equivalents + per-file notes, generated from a follow-up mockup), replacing the first indigo pass. Applied identically across all three portals. Not necessarily final forever, but this is the real palette now, not a stand-in:

- **Neutrals:** Tailwind's `slate` scale for text/borders/surfaces (`slate-900`/`slate-100` text, `slate-500` for muted/real data values, `slate-400` reserved for purely decorative use — chevrons, inactive nav icons, input placeholders — never for real data, per an explicit AA-contrast correction the reference called out; `slate-200`/`slate-800` borders, `slate-50`/`slate-950` page background so cards visually lift off the ground, `white`/`slate-900` for `Card`/`Header`/`Sidebar`/`Modal`/`AccountMenu` surfaces themselves).
- **Accent (primary actions, links, active nav/account-menu-item tint, focus rings):** `teal-700` for a solid fill behind white text (buttons, the primary CTA) and for plain link text on a white background — `teal-600` fails AA behind white and must never be used for a filled button or link text. `teal-600` is for icon tints/dots/decorative accents only (`IconBadge`, brand lockup square, focus-ring color). `teal-800` is for text sitting *on* a teal-tinted background (active Sidebar/AccountMenu item, the `admin`/`info` `Badge`). `teal-50` is the standard tint background. Dark mode: `dark:text-teal-400` for text, `teal-700` fill stays literal in both modes.
- **Destructive:** `red-600` solid (full-weight, confirmation-step only) / `red-50`+`red-200`+`red-700` tinted (`destructive-subtle`, inline row actions). **Success:** `green-600`/`green-700`/`green-50`. **Pending/warning:** `amber-600`/`amber-700`/`amber-50`. These three are semantic and deliberately **not** re-tinted when the accent changes — status reading must never depend on which accent is currently in fashion.
- **Corner radius:** cards/modals/brand-lockup squares `rounded-xl`; buttons/inputs/selects/icon badges/sidebar links/account-menu items `rounded-lg`; pills (`Badge`), `Avatar`, and the `Stepper`'s step circles stay `rounded-full`.
- **Shadows:** `Card` carries `shadow-sm` against the `slate-50`/`slate-950` page ground. `AccountMenu`'s open panel and `Modal` carry a heavier `shadow-lg` (a popover floating over content reads differently than a card sitting in the page flow). `Header`/`Sidebar` stay border-only, no shadow — they're chrome, not floating content.
- **Iconography:** `lucide-react`, used as decorative accents only — before a `Card`/section title (via `IconBadge`), next to each Sidebar/AccountMenu item, and in the `Header`'s brand lockup — never as the sole affordance for an action; every icon sits beside a real text label. The brand lockup (`Header`, and centered above the `h1` on every auth page) is a teal `rounded-lg`/`rounded-xl` square holding a `lucide-react` `activity` glyph — a deliberate placeholder mark, since no logo asset exists yet; swap it for a real one when it exists, everywhere it appears. Two things from the reference were deliberately not replicated: the floating rounded-card "device frame" around the whole screenshot (presentation chrome for the mockup image, not a real UI element) and fabricated staff fields the reference showed (a `Joined on` column, `ID: ST-2024-0012` staff codes) — `StaffMember` doesn't track either, and this was a visual pass, not a data-model change.
- **Dark mode:** Tailwind's default `dark:` variant (`prefers-color-scheme`, no in-app toggle) — every component pairs a light class with a `dark:` class; there is no separate dark stylesheet.
- **Typography:** Tailwind's default `font-sans` stack (no custom webfont actively wired — the Geist font loader in each `app/layout.tsx` sets CSS variables but nothing currently references them). `text-3xl font-semibold tracking-tight` for a page `<h1>` (via `PageHeader`, or hand-rolled for a personalized greeting like "Good morning, {name}" on the three portal home pages), `text-lg font-semibold` for `<h2>` (via `SectionHeading`/`Card` title), `text-sm` for body/labels, `text-xs` for meta text (badges, hints, ids). Buttons and badges are `font-semibold` (600), not `font-medium` — bumped from the first pass to match the reference's heavier button/pill weight.
- **Spacing:** Tailwind's default scale — `space-y-6` between major page sections, `space-y-4` inside a form, `p-5` card padding, `px-4 py-2` button padding. Patient's home page is a deliberate exception — see Layout conventions below.

## Layout conventions — Live

- **Shell structure:** sticky `Header` (`h-14` = 56px) above a content row; on Hospital/Owner that row is `Sidebar` + scrollable content, on Patient it's just the scrollable content (no sidebar — only one protected route exists today, see ARCHITECTURE.md).
- **Header brand lockup:** a teal `rounded-lg` square (the `activity` glyph placeholder mark) + "CarePulse" + a 1px vertical divider + the portal name (`Header`'s `portalName` prop, e.g. "Hospital") + (if present) a second divider + `subtitle` (e.g. the current hospital/role on the Hospital Portal). `Header` also takes an optional `backendUp: boolean | null` — when passed, renders a small "Connected"/"Not connected"/"Checking..." pill (green/slate tint) to the left of the account chip. Each `<Portal>Layout` fetches its own `getBackendHealth()` on mount and passes it down; a page that also wants to show connectivity in its own content (e.g. a "System" card) calls `getBackendHealth()` again independently — a second harmless idempotent request, not worth plumbing through Next.js layout→page props for.
- **Sidebar:** `w-56` expanded, `w-14` collapsed (desktop only, persisted per-portal to `localStorage`, read post-mount to avoid a hydration mismatch). Config-driven nav (`components/layout/nav.ts` per app) — add a nav item there, not by hand-editing `Sidebar.tsx` JSX, and only for routes that actually exist. Inactive nav icons are `slate-400` while the label text is `slate-600` (a deliberate two-shade split, not a mistake — matches the reference exactly); the active item's icon has no color override and inherits the tinted text color instead.
- **Sidebar footer panel** (`footer` prop, `mt-auto`, inset `rounded-xl bg-slate-50` block, hidden while collapsed): content is entirely owned by the calling `<Portal>Layout`, not the generic `Sidebar` component. Hospital shows "Acting within" / current hospital name / a "Switch hospital" link (`repeat` icon) that routes to `/` and reuses the existing hospital-switcher there — deliberately not a new mini-switcher or route. Owner shows "Signed in as" / the owner's name / "Platform owner". Patient has no Sidebar, so no footer.
- **Active nav state** is derived from `usePathname()`, never click state, so a deep link highlights the right item immediately.
- **Responsive breakpoint:** `md` (768px). Below it, the sidebar becomes an off-canvas drawer (slides in from the left under the header, with a dimmed overlay) instead of a persistent column; the hamburger menu button in the Header only renders on portals that have a sidebar at all.
- **Auth pages** (`/login`, `/register`, `/forgot-password`) are deliberately outside the shell — centered card on a neutral background (`bg-slate-50 dark:bg-slate-950`), no header/sidebar. Above the `Card`, every auth page repeats the same lockup as the Header (teal square + `activity` glyph) stacked vertically above the page's own `h1`/subline — see the Forms section below for what each route's specific header text is.
- **Page content:** every protected page's top-level element is `PageContainer` → a header (`PageHeader`, or a hand-rolled personalized greeting on the three home pages — see below) → a `space-y-6` stack of `Card`s, sometimes with a `grid grid-cols-1 sm:grid-cols-2 gap-4` pair of cards up top (e.g. "Your session" + "System" on every home page). List rows inside a `Card` use `divide-y divide-slate-200 dark:divide-slate-800`. **Patient's home page is the one deliberate exception**: no `PageHeader`/`PageContainer`, a standalone `max-w-[680px]` centered column with `py-12` — looser than the shared `max-w-3xl` convention, since Patient has no sidebar and no dense clinical lists yet (see the reference's own framing: "deliberately looser than the clinical portals").
- **Home-page greeting:** all three portal home pages replace the old generic `PageHeader title="CarePulse — X"` + "Backend status: ..." text with a personalized `getGreeting()` ("Good morning/afternoon/evening", computed from `new Date().getHours()`, purely presentational — no new data) + the user's first name, and a one-line subtext (current hospital+role on Hospital, a static "platform owner" line on Owner, an "Everything here is yours..." line on Patient). Backend connectivity moved from that page-level description line into the `Header`'s pill (see above) and, on Hospital/Owner, into a "System" card alongside "Your session".
- **Global actions live in the shell, not the page.** Nav to an existing page is only in the Sidebar (or the account menu — see below) — pages don't render their own duplicate link/button now that the shell always surrounds them.
- **Dashboards** — per-portal dashboard *content* (patient/hospital/owner) still not built (Phase 2+). Every existing page (status pages, hospital creation, AccessRole/access-request management) is now fully styled; what's still a placeholder is *new* clinical/monitoring content, not the pages that already exist.

## Account navigation vs. hospital navigation — Live (all three portals)

Two distinct, deliberately separate navigation surfaces in the Header, so the Sidebar stays scoped to one thing. `AccountMenu.tsx` is now wired into all three frontends' Headers (copied per app, like every other layout component — not pulled into `shared/`); each `<Portal>Layout` builds its own `items` list.

- **Sidebar — hospital/owner-application navigation only.** Routes for *doing the portal's actual work*: Hospital has Home and Access & Roles; Owner has Home and Hospitals; Patient has no sidebar yet (only one protected route today). Config-driven via `components/layout/nav.ts` per app. Never put a personal/account action here.
- **Account menu (top-right of the Header, `AccountMenu.tsx`) — personal/account actions**, not application pages. Hospital Portal: `Profile`, `Request hospital access`, `Settings`, divider, `Log out`. Owner/Patient Portals: `Profile`, `Settings`, divider, `Log out` (no request-access item — not applicable to those portals). `Profile`/`Settings` render disabled everywhere with a "Coming soon" hint — no page exists yet for either, on any portal; don't wire them up until those pages are actually built. On Hospital, `Request hospital access` **navigates to `/access-request`** (`router.push`, not a modal) — a dedicated page rather than a header dropdown, since it has real content of its own (search, a hospital list, every past request with its status).
- **`AccountMenu` itself is fully generic** (props: `userName`, `userEmail`, `items: AccountMenuItem[]`, `onLogout`) — keyboard accessible (arrow keys move focus between enabled items, Escape closes and returns focus to the trigger, Tab closes), closes on outside click and on route change, responsive (name label hidden below `sm`). Each portal's `<Portal>Layout` decides its own `items` array; the component never hardcodes what belongs in it. Each `AccountMenuItem` may carry an `icon` (`lucide-react`, decorative) and an `active` flag — `active` is computed by the calling Layout (via its own `usePathname()`), not derived inside `AccountMenu`, and tints the item the same teal as an active Sidebar entry when the item represents the page currently being viewed (currently only Hospital's "Request hospital access" while on `/access-request`).
- **Trigger is a pill**, not a plain button: `Avatar` flush-left, name, a `chevron-down`/`chevron-up` (open state) — border `slate-200` normally, `teal-300`/teal-tinted background while open.
- **Why this split:** "which hospital am I acting within, and what can I do there" (Sidebar) is a different question from "what does this account itself want to do, regardless of hospital" (account menu). Requesting access to a *new* hospital is the second kind of action — it's about the account, not about the hospital currently selected — which is why it isn't on `/access` or in the Sidebar at all.
- **Popover panel styling:** `w-60`, right-aligned (`right-0 top-full`), `rounded-xl`, `shadow-lg` — a floating popover, not a `Card`, so it gets the heavier shadow (see Color & typography above).

## `/access-request` (Hospital Portal only) — Live

The dedicated home for requesting hospital access, reachable only from the account menu (not the Sidebar — see the split above). Two cards, same shell/primitives as every other page:

- **Find hospitals:** a search `Input` above a plain list of bordered rows (name + id, no card-grid/icon treatment — matches the rest of the app's list convention rather than the icon-heavy reference this was built from). A hospital already blocked by a `pending`/`active`/`rejected` request doesn't appear; one that's `removed` or `cancelled` does, since re-requesting is allowed for those.
- **My requests:** every request, any status, with a `Badge` (`toneForStatus`) and a "Requested on" date (`MyAccessRequest.createdAt`, added specifically for this). A **Cancel** button appears only on `pending` rows (`POST .../cancel`) — the only mutating action available here besides requesting itself; every other status is read-only history.
- Loading/empty/error/already-requested/success states follow the same pattern as every other page (`LoadingState`/`EmptyState`/`Alert`, per-row `disabled` + label swap while a request/cancel is in flight).

## Staff management — Live (Hospital Portal)

`/access` is staff-first: **Staff** is the only permanently-visible card. Adding/reviewing staff lives behind a `Modal`; role management is an inline expand/collapse panel in its own card, not a modal:

- **Staff card** (`canManageStaff`-gated: admin, or a staff member whose current AccessRole includes `staff.manage`): a search `Input` (client-side, filters the already-fetched list — no new query param) above the staff list. `isAdmin` only, a prominent **Add staff** button sits in the card header, its label showing a pending-request count when there's a backlog (`Add staff (3)`).
- **Each staff row** shows a `disabled` `Badge` when suspended, and up to three actions depending on state and who's viewing:
  - **Edit** (`isAdmin` only — a `staff.manage` holder can't even list AccessRoles, so this is never shown to them): swaps the row's action area for an inline `Select` of active roles + Save/Cancel — no modal, no navigation. `PATCH /api/hospital/staff/:id/role`.
  - **Disable** / **Enable** (`canManageStaff`-gated, single toggle button whose label follows the row's current status): a reversible suspension, distinct from Remove — `POST /api/hospital/staff/:id/disable` or `.../enable`. Disable is peer-protection-aware exactly like Remove (`StaffMember.canManageStaff`, disabled + tooltip when blocked); Enable has no such restriction.
  - **Remove** (`canManageStaff`-gated, only shown while `active` — a disabled member has nothing to remove from *right now*, re-enable first): unchanged — confirmation `Modal`, `DELETE /api/hospital/staff/:id`, peer-protection-aware disabling.
- **`AddStaffModal`** (`components/access/AddStaffModal.tsx`, `isAdmin`-gated): two stacked sections in one modal, not two entry points, since both end at "one more active staff member." **Add directly** — name/email/role form, `POST /api/hospital/staff`, success copy differs on whether a new account was created (temp password emailed) vs. an existing one was granted access. **Pending requests** — the same approve (role `Select` + Approve/Reject) review that used to be its own always-visible card, moved in as-is. Rendered by the page only while open (`{open && <Modal.../>}`), not passed an `open` prop — mount/unmount is what resets its internal state on every open.
- **`ManageRolesPanel`** (`components/access/ManageRolesPanel.tsx`, `isAdmin`-gated) is rendered **inline inside the Roles & Permissions Card**, toggled by a "Manage roles" button with a rotating `ChevronDown` — not a `Modal`. Same content as before (create-role form + role list + edit + delete, via internal view-switching `"list" | "edit" | "delete"`) but as plain content instead of a dialog overlay, so expanding it pushes the rest of the page down rather than opening a popup on top of it. Conditionally mounted only while expanded (`{rolesExpanded && <ManageRolesPanel .../>}`), same mount/unmount-resets-state pattern as `AddStaffModal`. Edit/Delete behave exactly as before (`PATCH`/`DELETE /api/hospital/access-roles/:id`, delete blocked with a 409 — shown via `Alert` inline — while any *active* staff member still holds that role).

## Hospital lifecycle (Owner Portal) — Live

`/hospitals`'s "Existing hospitals" card lists every hospital (active and disabled — unlike the staff-facing "browse hospitals to request access to" list, which excludes disabled ones). Each row shows a `disabled` `Badge` when paused, and two actions:

- **Disable** / **Enable** (single toggle button whose label follows the row's current state, no confirmation needed — it's fully reversible): a pause, not a delete. `POST /api/owner/hospitals/:id/disable` or `.../enable`. Every staff/admin membership and AccessRole is left completely untouched underneath — only access is cut off, immediately, even for an already-issued session (`verifyActiveMembership`, `getCurrentHospitalContext`, `resolvePermissions`, `assertHospitalAdmin`, `assertCanManageStaff`, and `requestAccess` all additionally check `Hospital.isActive` and fail closed). A disabled hospital also disappears from "Your hospitals" (Hospital Portal home) and the request-access browse list.
- **Delete** (`destructive-subtle`, opens a confirmation `Modal` before doing anything — irreversible, so the frontend asks first even though the backend doesn't): permanently deletes the Hospital record along with every AccessRole and HospitalMembership (staff *and* admin) tied to it. `DELETE /api/owner/hospitals/:id`. Deliberately does **not** touch the underlying User accounts — an admin or staff member who only ever worked at that one hospital keeps their login, they just have no hospital access left; only the hospital-specific records disappear.

## Forms — Live

Every form field is a `TextField` (or bare `Label`+`Input`/`Select` where a composed field doesn't fit, e.g. the hospital search box's custom dropdown). This gives every field, for free: a visible associated `<label>` (via `useId()`), consistent height/border/focus ring, a disabled state, and an `aria-invalid`/red-border/error-text state when an `error` prop is passed. Submit buttons show a loading label (`"Logging in..."`) and `disabled` while a request is in flight — unchanged from before, just via `Button` now. Success/failure feedback goes through `Alert`, never inline unstyled text.

- **`/register` (Patient, Hospital) is a 3-step flow**, using `Stepper` above the `Card`: **Details** (name, email, phone — client-side only, no request; "Continue" just advances) → **Password** (the actual `register()` API call fires here, on success advancing to Verify; has a "← Back" link to Details) → **Verify** (the existing OTP step, unchanged). The step-1→2 split is presentational only — the backend still receives one `register({name, email, phone, password})` call, same as before, just gathered across two screens instead of one.

## How to use this file if the palette changes again

Replace the color/typography section above with the new palette and note any component whose Tailwind classes need to change. The structural conventions (shell dimensions, breakpoint, `PageContainer`/`Card`/form patterns) can stay as-is unless the new direction specifically calls for a different structure — this is implementation guidance, not a brand book.
